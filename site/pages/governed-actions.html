Governed actions

From a proposal to an accountable action

Deciding what to do is only the beginning.

A governed action expresses an intended change so it can be examined, authorized, approved and recorded before reaching an external system. This is a conceptual explanation of the behavior illustrated by the public technical demo, not private implementation topology.

Questions along the action path

  1. Proposed action

    What object should change, and what precisely is being proposed? A suggestion alone does not execute a write.

  2. Authorization & governance

    Is this action permitted in the application's scope and under the operator's confirmed configuration?

  3. Human approval

    Is approval bound to this intended action? The technical demo illustrates an approval binding as a structural prerequisite, with requester and approver separated.

  4. Durable intent & external execution

    The technical refund demo records the attempt before the external call. A lost response is classified honestly; approval does not guarantee that an external action succeeds.

  5. Evidence & audit

    Retain the decision path and observations so an operator can inspect what was decided and what remains uncertain.

Evidence verification has a scope

Approval-task evidence only. The technical demo verifies the approval task's tamper-evident evidence chain. Command records, execution attempts, external observations and audited write steps are retained and auditable; they are not presented as part of that same hash chain.

The whole system audit database is not claimed to be one tamper-evident chain. Retained records and chain verification answer different questions. In the technical refund demo, the reconciliation verdict is derived from the recorded command and observations, not stored as a verdict, and never rewrites command truth.
